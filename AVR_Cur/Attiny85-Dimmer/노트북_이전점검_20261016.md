# 노트북 이전 점검 — 2026-10-16

후속 작업: 같은 날 v4.6 최대출력 제한 시험 버전을 만들면서 호스트 C++ 컴파일러와
simavr 개발 라이브러리를 프로젝트 내부에 준비했다. 현재 재시험 방법은 `test/README`,
현재 변경 내용은 `v4_6_최대출력_제한.md` 참고. 아래는 이전 직후 v4.5 점검 당시 기록이다.

현재 프로젝트에서 v4.5 펌웨어를 수정하고 HEX를 다시 만들 수 있다.
노트북에서 클린 빌드한 HEX는 가져온 현장 시험용 v4.5와 SHA256이 일치했다.
펌웨어 소스, 점화 상수, platformio.ini, 배포 HEX는 변경하지 않았다.
MCU 업로드, 퓨즈 쓰기 및 실제 부하 시험은 수행하지 않았다.

## 현장에서 사용할 작업 위치와 명령

- 수정할 파일: 이 프로젝트의 `src/main.cpp`.
- `release/.../source`와 `ATtiny85_Dimmer_v4_5_FieldTest_20261015/source`는 배포 당시 사본이다. 여기서 수정하면 루트 프로젝트 빌드에 반영되지 않는다.
- 프로젝트 루트의 PowerShell 터미널에서 다음 명령을 실행한다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build-field.ps1 -Clean
```

스크립트는 `.pio/core`의 도구를 선택해 클린 빌드, 새 ELF 역어셈블,
ISR 시간 검사, HEX 해시 비교까지 수행한다. 실행 정책 옵션은 해당 프로세스에만 적용한다.
성공 시 출력되는 `Built HEX` 경로가 이번 빌드 결과다.

```text
.pio/build/attiny85/firmware.hex
```

SmartProg2에서 수정본을 기록할 때는 **이 빌드 결과 파일을 선택**한다.
루트 `firmware.hex`와 버전명이 붙은 HEX, ZIP 안의 HEX는 자동으로 갱신되지 않는다.
소스 수정 후 `CHANGED`가 나오면 이전 배포본과 달라졌다는 의미이며, 그 자체는 빌드 오류가 아니다.
시간 검사 실패 시 해당 변경을 검토해야 한다. 스크립트 통과는 기능/실보드 시험을 대신하지 않는다.

현재 workspace의 `build` 별칭과 VS Code 일반 빌드 버튼은 이 스크립트에 연결하지 않았다.
이번에 검증한 환경을 재현하려면 위 명령을 사용한다.

## 이전 과정에서 발견한 차이와 조치

1. **빌드 도구 버전 차이**
   - 노트북 PlatformIO Core는 6.1.19, 가져온 `.pio/core`의 기록은 6.2.0이었다.
   - 가져온 SCons 4.41101.0은 노트북 Core가 요구하는 4.40801.0과 달라 설치를 시도했다.
   - 노트북에 이미 설치된 SCons 4.40801.0을 `.pio/core/packages/tool-scons-4.40801.0`에 추가 복사해 해결했다. 기존 도구는 보존했다.
   - 이전 Core 버전 기록 때문에 `Obsolete PIO Core` 경고가 남지만, 검증한 빌드는 성공한다.
   - 이번 빌드: Atmel AVR 5.1.0 / ATTiny Arduino 1.5.2 / AVR GCC 7.3.0.
   - 사용자 기본 PlatformIO 폴더의 Atmel AVR는 5.3.0이다. 일반 빌드와 검증 환경을 혼동하지 않도록 스크립트에서 프로젝트 내부 도구를 선택한다.

2. **Git 변경 이력 누락**
   - `.git` 폴더는 비어 있으며 `git status`가 저장소로 인식하지 못한다.
   - 현재 파일과 `backup` 디렉터리는 있지만 커밋 이력/브랜치/원격 정보는 확인할 수 없다.
   - 기존 이력이 필요하면 원래 PC의 저장소 또는 원격 저장소에서 복원해야 한다.
   - 현장에서 변경하기 전에는 수정할 소스를 별도 버전 폴더에 복사해 둔다.

3. **시험 개발 도구 일부 누락**
   - `test/README`에 있는 이전 PC의 `C:/msys64/ucrt64/bin`과 `tool-simavr` 라이브러리는 찾지 못했다.
   - 호스트 C++17 시험을 다시 빌드할 g++/clang++도 확인되지 않았다. AVR용 g++는 Windows 호스트 시험용 컴파일러가 아니다.
   - 가져온 `.pio/test_timing.exe`와 `.pio/simavr_timing.exe`는 실행 가능했다. 실행 시 설치된 Git의 `C:/Program Files/Git/ucrt64/bin`을 해당 프로세스의 PATH에 추가했다.
   - `test_timing.exe`는 빌드 당시 소스를 포함한 실행 파일이므로, 앞으로 `src/main.cpp`를 바꿔도 예전 EXE 실행만으로 새 소스 회귀시험을 대체할 수 없다.
   - 시험 프로그램까지 수정·재컴파일하려면 C++17 호스트 컴파일러 및 simavr 개발 라이브러리가 추가로 필요하다.
   - `.pio`는 `.gitignore`에서 제외되어 있다. 이번에 확인한 도구와 시험 실행 파일은 Git만으로 옮길 경우 포함되지 않는다.

4. **이전 PC 경로가 남은 안내**
   - `SmartProg2_업로드_가이드.txt`의 `D:/01_AllData/...`는 이전 PC 경로다.
   - 이 노트북의 작업 루트는 `C:/01_DATA/03_Embedded_Proj/Attiny85-Dimmer`이다.
   - `Attiny85-Dimmer.code-workspace`에도 사용자 경로가 고정되어 있다. 현재 노트북에서는 대소문자 차이만 있어 파일은 존재하지만 다른 계정으로 옮기면 재확인이 필요하다.
   - 새 스크립트는 프로젝트 위치와 USERPROFILE을 사용한다. `test/README` 앞부분에 노트북용 실행 방법을 추가했다.

## 펌웨어 설정과 실보드 확인 범위

현재 소스는 내부 RC 8MHz, PB0 게이트 / PB1 상태 / PB2 ZC / PB3 ADC3 설정이다.
50/60Hz 공용으로 실측 반주기에 비례한 위상을 사용한다.
부팅 대기 명목 1초, 연속 8반주기 동기화, ADC 899 이하 ON / 900 이상 OFF,
위상 기준 133~308, 보정 2, 종료 여유 16이 v4.5 배포본과 일치한다.
소스의 동기화 손실/OFF 처리, ZC 폭 확인, ISR 공유값 보호 및 시간 예산을 점검했다.
이번 소프트웨어 점검 범위에서는 펌웨어 수정이 필요한 문제를 발견하지 못했다.

문서와 설정에 기록된 퓨즈는 E2/DF/FF이며 실제 칩의 값은 읽지 않았다.
HEX 파일이 퓨즈를 설정하는 것은 아니다.
SmartProg2 프로그램/INF 파일 존재만으로 드라이버 정상 설치나 장치 연결 성공을 확인할 수는 없다.
현장 투입 전 실제 프로그래머에서 ATtiny85 인식, 퓨즈 읽기, Flash 기록 후 Verify를 확인한다.

실제 50Hz 부하 시험은 기존 기록에서도 미실시 상태다.
최저출력의 짧은 게이트 펄스에서 실제 트라이악이 점화되는지와 고출력 흔들림은
`50Hz_60Hz_검증가이드.md` 및 현장 시험 안내에 따라 실제 장비에서 확인해야 한다.

## AVR 시뮬레이션 실행 방식

노트북에서 새로 빌드한 ELF를 `avr-objcopy -O binary`로 변환하고,
가져온 `.pio/simavr_timing.exe`에 입력했다. 시험 실행 파일 자체는 재컴파일하지 않았다.
결과 로그는 `.pio/simavr-laptop-check.log`에 저장했다.
처음에는 55초 실행 제한으로 일부 조건만 수행되어 종료했으며, 이후 전체 시험을 다시 실행했다.
전체 재실행은 42/42조합 통과 및 종료 코드 0으로 완료되었다.
50/60Hz × CPU 6.8/8.0/9.2MHz × 최대/최소 출력 × ZC 폭 3종의 36조합과,
ON 경계 부근 4390mV 입력 6조합을 확인했다.

시험 코드에는 simavr의 ATtiny85 Timer1 CTC 모델 누락을 보완하는 처리가 있다.
따라서 이 시험은 실제 Timer1 주변장치와 옵토커플러/트라이악/부하를 독립적으로 검증하지 않는다.
