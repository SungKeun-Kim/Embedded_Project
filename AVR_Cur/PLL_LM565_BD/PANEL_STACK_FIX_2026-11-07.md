# ATmega16A 화면·키 동작 이상 수정

## 보고된 증상

ATmega16A 갱신 후 P/L이 068로 잘못 표시되고, PULSE/CONT. 선택과 REMOTE 조작이 화면에 반영되지 않았다. 재기동 후에는 화면이 계속 바뀌는 이상 동작도 보고되었다.

## 확인된 결함

기존 링크 결과는 CSTACK과 RSTACK을 각각 **32바이트**만 예약했다. 전체 SRAM에 여유가 있어도 이 예약을 초과하는 사용을 막아 주지 않는다.

IAR의 실제 함수별 스택 목록을 합산하면 다음 경로의 CSTACK은 일반 실행 **22바이트 + ISR 17바이트 = 최소 39바이트**가 필요하다.

```text
main → funKey_scan → funRemoteKey_prog → funRemote_on → frequency
     → lcd_locate → lcd_write_command → lcd_write → write_nibble
이 실행 중 TIMER0_COMP_interrupt 발생
```

기존 예약보다 7바이트 크다. CSTACK은 데이터 주소 0x60~0x7F에 있었고, 아래쪽은 MCU 레지스터 영역이다. 스택 경계 초과는 화면·키·인터럽트 상태의 이상을 일으킬 수 있다. 이 결함은 컴파일 결과로 확인했지만, 보고된 모든 증상의 원인이 이것뿐인지는 실물 재시험으로 확인해야 한다.

앞선 시험은 알고리즘과 총 메모리 사용량을 검증했으나 ATmega16A의 호출 경로별 스택 예산 검사를 빠뜨렸다.

## 수정과 검사

- `sonic.ewp`의 CSTACK을 128바이트, RSTACK을 128바이트로 늘렸다.
- SRAM 총 배치는 498바이트에서 **690바이트/1,024바이트**로 바뀌었다. Flash 이미지 크기는 5,106바이트다.
- [스택 검사 스크립트](./tests/check_avr_stack.py)를 추가했다. 원래 빌드에서는 실패하고 수정한 빌드에서는 통과한다.
- ATmega16A 빌드/업로드 시 검사하도록 연결했다. 알려진 함수 호출 경로와 ISR 1회의 사용량, 추가 16바이트 여유를 비교한다. 라이브러리/간접 호출 내부와 실물 최대 사용량을 완전히 분석하는 도구는 아니다.
- P/L 표시값을 상수로 바꾸거나 보호 로직을 끄지 않았다. 첫 수정은 확인된 스택 결함에 한정했다.
- IAR 빌드 오류 0, 기존 미사용 변수 경고 4개. CSTACK 39+16≤128, RSTACK 28+16≤128로 검사 통과.

## 기록 상태

첫 시도는 USBasp의 `target does not answer` 오류로 대상 확인 단계에서 중단되었고, 쓰기는 수행하지 않았다. 이후 사용자가 연결·전원을 확인한 뒤 **수정본의 실제 기록과 검증을 완료**했다.

- Flash 5,106바이트 기록·쓰기 검증·별도 재검증 통과.
- EEPROM 512바이트 복원·검증 통과. 최초 ATmega16A 업로드 전 백업과도 SHA-256이 동일하다.
- 퓨즈/잠금값은 lfuse=0xFF, hfuse=0xC9, lock=0xFF로 전후 동일.
- [장비 백업과 수정본 HEX](./.build/backups/ATmega16A_upload_20261107_235237_9bb2d4f1/)
- [업로드 로그](./.build/atmega16a_panel_fix_retry_20261107_235236.log)
- 수정본 HEX SHA-256: `C8053E6A44B60370AA8B3FC150376946F963EF5F1D30154083E830D6A29A8729`

실물 확인 항목은 P/L 노브 반응, PULSE/CONT. 표시 전환, REMOTE에 따른 STOP/RUN 및 주파수 표시 전환이다. 프로그래머의 기록 검증과 별도로 사용자 관측이 필요하다.
